План реалізації

wsc — запуск WebStorm-команд одним викликом

CLI, що читає run-конфігурації WebStorm через вбудований MCP Server і запускає обраний набір одночасно — кожна команда у власній вкладці Run/Debug або Terminal, з ручним fallback на локальний термінал, якщо MCP вимкнено. План розрахований на ручну розробку: кожна фаза — контракт і перевірка, а не готовий код.

Node ≥ 18, ESM 11 фаз 2 залежності Тести в кожній фазі Тестовий проєкт: demo-app

Як читати план

Кожна фаза має рядок міток: хто її виконує і чим можуть допомогти агенти. Розділ «Роль агентів» у довіднику — той самий список одним поглядом. Чекбокси зберігаються у браузері (localStorage) — прогрес не зникне між сесіями, але живе лише в цій вкладці браузера.

Правило кожної фази: фаза вважається закритою тільки тоді, коли для написаного в ній коду є юніт-тести і вони проходять — не одним «здавальним» прогоном наприкінці (фаза 10), а одразу поряд із кодом. Тому в кожній фазі нижче є окремий файл test/*.test.js у списку файлів і пункт «тести написані й проходять» у переліку перевірки. Код, який важко юніт-тестувати напряму (жива IDE, інтерактивний @inquirer/prompts-UI, реальний spawn термінала), навмисно розбивається на чисту логіку (яка тестується) і тонку обгортку з побічними ефектами (яка перевіряється руками за чеклистом).

00 · передумови

Передумови середовища

Без цього кроку решта плану технічно неможлива — MCP Server вимкнений за замовчуванням, а без нього немає окремих вкладок.

Пишеш ти

Дії

  1. WebStorm → Settings → Tools → MCP Server → увімкнути Enable MCP Server.
  2. Там само увімкнути Run shell commands or run configurations without confirmation (Brave Mode) — інакше кожен запуск чекатиме підтвердження в UI.
  3. Прочитати фактичний порт прямо з цього ж екрана Settings — він показаний у вигляді посилань http://127.0.0.1:<port>/sse і /stream. Порт не з якогось передбачуваного діапазону (у нашому випадку — 64542) і ніде не зберігається у файлі, який CLI міг би прочитати — перевірено: mcpServer.xml містить лише enableMcpServer/enableBraveMode, без порту.
  4. Зафіксувати порт, щоб CLI не вгадувало його щоразу: Help → Edit Custom VM Options → додати рядок -Didea.mcp.server.force.port=<обраний порт> → перезапустити WebStorm. Після цього порт стабільний і його можна прописати в конфігу CLI (фаза 2) замість сканування.
  5. Перевірити наявність термінал-емулятора для fallback-шляху: command -v gnome-terminal (на цій машині вже є).

02 · mcp-клієнт

MCP-клієнт: виявлення й підключення

Найризикованіша частина проєкту — тут CLI вперше говорить із живою IDE. Зробити окремо від усього іншого й перевірити руками на реальному demo-app, перш ніж будувати щось поверх.

Пишеш ти — тут найважливіше не делегувати

Файли

  • src/mcp/discovery.jsпорт бере з WSC_MCP_PORT / --mcp-port (той, що зафіксований у фазі 0 через force.port); скан діапазону — лише best-effort fallback, не основний шлях
  • src/mcp/client.jsобгортка над @modelcontextprotocol/sdk: connect + typed callTool
  • scripts/mcp-probe.jsручний скрипт для цієї фази — не частина CLI, викинути або лишити в scripts/ як діагностику
  • test/discovery.test.jsюніт-тести discoverPort() проти фейкового HTTP-сервера в тесті (порт відповідає/не відповідає/відповідає не-MCP) — без живої IDE

Контракт

// src/mcp/discovery.js
export async function discoverPort(opts?: {
  explicitPort?: number,            // з WSC_MCP_PORT env або --mcp-port
  fallbackRange?: [number, number], // best-effort скан, якщо explicitPort не задано — ненадійно, лише останній шанс
}): Promise<number | null>

// src/mcp/client.js
export async function connectMcp(port: number): Promise<McpClient>
export interface McpClient {
  callTool(name: string, args: object): Promise<unknown>
  close(): Promise<void>
}

Транспорт — StreamableHTTPClientTransport з SDK, база http://127.0.0.1:<port> (підтверджені шляхи /sse і /stream). Обов'язково викликати initialize перед першим tools/call — SDK робить це сам при client.connect(transport).

Чому не сканування діапазону: порт ніде не публікується файлом (перевірено — mcpServer.xml зберігає лише enableMcpServer/enableBraveMode), і реальне значення на цій машині — 64542, поза «типовим» діапазоном 64342+. Без зафіксованого через force.port порту з фази 0 CLI довелося б сканувати сотні портів навмання — тому явний порт (env/конфіг) є основним шляхом, а скан лишається лише деградованим fallback.

Перевірка

Збережи сирий JSON-результат get_run_configurations зі demo-app в test/fixtures/run-configurations.json — він знадобиться як мок-дані для фаз 3–6, щоб не тримати живу IDE запущеною під час тестів.
03 · резолвер

Нормалізація даних і резолвер імен

Чисті функції без побічних ефектів — і тому найзручніше місце для юніт-тестів на справжніх даних.

Пишеш ти Агент: рев'ю edge-кейсів парсингу

Файли

  • src/args.jsnode:util.parseArgs-обгортка + парсинг позиційних name[:run|:debug]
  • src/resolve.jsпошук конфігурації за іменем, злиття пресету з CLI-аргументами
  • test/fixtures/run-configurations.jsonзбережено з фази 2
  • test/args.test.jsюніт-тести splitNameMode на іменах із двокрапками (api > repro:stale-job:debug тощо)
  • test/resolve.test.jsюніт-тести резолву на фікстурі з 13 реальних конфігурацій

Ключове правило парсингу

Розділяти name:mode по останньому : — і тільки якщо суфікс дорівнює run чи debug. Причина: самі імена містять двокрапки, напр. client > bundle:build — без цього правила резолвер відріже не той шматок.

Але самого правила недостатньо. У demo-app є конфігурація api > repro:stale-job:debug, суфікс якої дорівнює debug — синтаксичне правило розрізало б її навпіл. Розв'язати це можна лише даними: спершу перевіряємо, чи весь токен збігається з іменем, яке повернула IDE (isKnownName), і лише якщо ні — пробуємо різати. Без списку імен splitNameMode деградує передбачувано; це задокументовано й закріплено тестом.
splitNameMode("web:debug")
// → { name: "web", mode: "debug" }

splitNameMode("client > bundle:build")
// → { name: "client > bundle:build", mode: "run" }        // суфікс не run/debug

splitNameMode("api > repro:stale-job:debug", { isKnownName })
// → { name: "api > repro:stale-job:debug", mode: "run" }   // це саме ім'я з IDE

splitNameMode("api > repro:stale-job:debug:debug", { isKnownName })
// → { name: "api > repro:stale-job:debug", mode: "debug" } // подвоєний суфікс = вихід

Резолв імені

  1. Точний збіг (case-sensitive)
  2. Case-insensitive збіг
  3. Префіксний збіг — лише якщо кандидат один; addon у demo-app підходить трьом конфігураціям, тому це помилка зі списком, а не здогадка
  4. Інакше — помилка з «Did you mean …» (Левенштейн по всіх іменах) і зупинка до запуску будь-чого

06 · виконання

Виконання через MCP — основний шлях

Ядро продукту: перетворити резолвлений список {name, mode}[] на виклики MCP, які реально відкривають вкладки.

Пишеш ти — тут уся цінність проєкту

Файли

  • src/mcp/execute.jsобгортки над execute_run_configuration і execute_terminal_command
  • src/exec/planBuilder.jsрезолвлений список → список викликів MCP з урахуванням обраного режиму виконання (термінал/run-config)
  • test/planBuilder.test.jsюніт-тести на фікстурі з фази 2: правильний вибір інструмента (run-config/terminal), правильна побудова debug-команди, без жодного реального виклику MCP (мок-клієнт)

Два способи запуску одної конфігурації

СпосібВикликДе з'являється вкладка
Run/Debug tool windowexecute_run_configuration({ configurationName })Нативна вкладка з іменем конфігурації — IDE сама її створює/перевикористовує
Terminal tool windowexecute_terminal_command({ command, reuseExistingTerminalWindow: false })Нова вкладка Terminal на кожен виклик

Для debug-режиму в терміналі команда, яку передаєш у execute_terminal_command, має включати --inspect-brk (через NODE_OPTIONS) або запускати альтернативний debug-скрипт, якщо він є в get_run_configurations (у demo-app такі вже готові: api > repro:stale-job:debug, mailer > debug:log).

Контракт

// src/exec/planBuilder.js
export function buildExecutionPlan(
  resolved: { name: string, mode: "run"|"debug" }[],
  runConfigs: RunConfigInfo[],       // з get_run_configurations
  target: "run-window" | "terminal"
): McpCall[]

07 · mcp недоступний

MCP недоступний: retry / fallback

Точний UX, який ти визначив: повідомлення з двома опціями, не мовчазний фолбек.

08 · термінал-fallback

Термінальний fallback (кілька вкладок)

Коли MCP недоступний — все одно спробувати окремі вкладки, тільки вже термінал-емулятора ОС, а не WebStorm.

Пишеш ти — адаптер gnome-terminal Агент: адаптери konsole/macOS/Windows за тим самим інтерфейсом

Файли

  • src/fallback/terminalTabs.jsдетект емулятора + виклик через spawn
  • src/fallback/singleTabPool.jsостанній рубіж: один процес-пул із кольоровими префіксами, як у першій версії плану
  • test/terminalTabs.test.jsюніт-тести порядку детекту й побудови команди для кожного емулятора з ін'єкованим (фейковим) резолвером PATH — без реального spawn

Підтверджена команда для gnome-terminal

gnome-terminal \
  --tab --title="web" -- bash -c "cd web && npm run dev; exec bash" \
  --tab --title="api"    -- bash -c "cd api && npm run debug; exec bash"

Кожен --tab — окрема вкладка того самого вікна. exec bash в кінці лишає вкладку відкритою після завершення/падіння процесу, щоб побачити вивід і код виходу.

Порядок детекту

  1. gnome-terminal (підтверджено на цій машині)
  2. konsole --new-tab
  3. macOS: osascript → tell application "Terminal" to do script
  4. Windows: wt (Windows Terminal) з прапорцем new-tab
  5. Нічого не знайдено → singleTabPool.js, з явним попередженням у консолі, що вкладки об'єднані

Приймальний чекліст (наскрізний, на demo-app)

Довідник · MCP-інструменти

Витягнуто з байткоду mcpserver.jar цієї конкретної інсталяції WebStorm 2026.2.1 (build 262.9437.145) — сигнатури можуть відрізнятись між версіями IDE, тому варто перевірити на своїй перед фазою 2.

ІнструментПараметриНотатка
get_run_configurations projectPath, filePath? Повертає лише name, description ("npm"/"Node.js") і supportsDynamicLaunchOverrides — без workingDirectory/envs, попри те що каже байткод (перевірено на живій IDE)
execute_run_configuration projectPath, configurationName, waitForExit?, timeout?, programArguments?, workingDirectory?, envs? Відкриває/перевикористовує нативну вкладку Run/Debug з іменем конфігурації
execute_terminal_command projectPath, command, executeInShell, reuseExistingTerminalWindow, timeout, maxLinesCount, truncateMode reuseExistingTerminalWindow: false → нова вкладка Terminal на кожен виклик. Чекає до timeout мс, збирає вивід — сам процес лишається жити в тлі
projectPath обов'язковий на практиці. Один MCP-сервер обслуговує усі відкриті вікна IDE. Якщо проєктів більше одного, будь-який виклик без projectPath повертає isError: true зі списком відкритих проєктів — тому McpClient прив'язується до проєкту при створенні й підставляє його в кожен виклик.
Помилки приходять як успішна відповідь. Провал інструмента — це { isError: true, content: [{ type: "text", text: "..." }] }, а не виняток. Без явної перевірки isError CLI сприйме текст помилки за дані.
Brave Mode обов'язковий для обох execute-інструментів — без нього кожен виклик показує діалог підтвердження в UI IDE, що ламає одночасний запуск кількох команд.
