# Власні CLI-команди у пресеті — дизайн

Дата: 2026-09-21 · Статус: затверджено в діалозі, чекає на рев'ю файлу

## Мета

`wsc` має вміти запускати звичайні shell-команди — одну або послідовність — без run-конфігурацій
WebStorm. Команду з іменем додають у пресет під час `--configure`. Під час запуску відкривається
Terminal-вкладка, названа так само, як запис у пресеті.

## Рішення, прийняті в діалозі

| Питання | Рішення |
|---|---|
| Де живе команда | Тільки всередині пресету. Виклику з CLI за іменем немає. |
| Помилка в послідовності | Зупинка на першій помилці (`&&`). Вкладка лишається відкритою. |
| Де відкривається вкладка | Terminal-вкладка IDE; без IDE — вкладка ОС-терміналу (наявний fallback). |
| `cwd` | Не додається. `cd server && …` пишеться в самій команді. |
| Підтвердження перед запуском чужого пресету | Немає. Замість нього команди завжди друкуються перед запуском. |

## Не входить у обсяг (YAGNI)

- Виклик власної команди з CLI (`wsc "seed db"`) та пов'язане правило пріоритету імен.
- Окремий каталог команд (`commands: {…}`) з посиланнями з пресетів.
- Поле `cwd`, режим `onError`, редагування тексту наявної команди в `--configure`.
- Явне підтвердження на запуск команд із пресету.

## 1. Модель даних

Запис пресету з масивом `commands` — власна команда:

```json
{ "name": "seed db", "mode": "terminal", "commands": ["npm i", "npm run seed"] }
```

- Нового значення `mode` немає, `MODES` у `src/modes.js` не змінюється. `command` у `MODES` дало б
  хибний токен `wsc foo:command` і зайвий пункт у select. Використовується наявний `terminal`.
- Версія схеми лишається 1. Так само вчинили при додаванні `terminal`. Старіший `wsc` прочитає запис
  як run-конфігурацію `seed db` і зупиниться з "unknown configuration", тобто нічого хибного не запустить.
- `parseEntry` у `src/presets/store.js` перевіряє `commands`. Це має бути непорожній масив непорожніх
  рядків без `\n`. Порушення дає `PresetConfigError` з назвою файлу й номером запису. Запис з
  `commands` і `mode`, відмінним від `terminal`, теж помилка: значення суперечить типу запису.
- `serializeConfig` записує `commands` після `mode`. Порядок ключів фіксований, тому перезапис
  незміненого пресету не дає diff.
- Тип `PresetEntry` отримує `commands?: string[]`. Хелпер `isCustomEntry(entry)` живе в `store.js`
  і є єдиним місцем цієї перевірки.

## 2. Резолвінг

`src/resolve.js`:

- `PlanEntry` стає об'єднанням. Звичайний запис має `config: RunConfigInfo`. Власний має
  `commands: string[]` і не має `config`. Обидва мають `name`, `mode: 'terminal'` і `source`.
- `buildLaunchPlan()` для власного запису пропускає `resolveName` і не потребує каталогу IDE.
- Ключ у внутрішньому `Map` для власного запису — `custom:<name>`, для звичайного — ім'я конфігурації.
  Власна команда й run-конфігурація з однаковою назвою не зливаються. Дві власні з однаковою назвою
  з різних пресетів зливаються за наявним правилом: перша позиція, остання перемагає.
- CLI-запити (`requests`) резолвляться, як і раніше, лише проти імен IDE. Змінити власний запис з
  командного рядка не можна.
- `formatPlan()` не змінюється: власний запис виглядає як `seed db  terminal  (preset)`.

## 3. План запуску

`src/exec/planBuilder.js`:

- `usesTerminal()` уже повертає `true` для `mode === 'terminal'`. Власний запис завжди йде в термінал,
  незалежно від `--target`. `:debug` з CLI на нього не діє.
- `buildExecutionPlan()` для власного запису не викликає `commandFor`. Команда — це
  `commands.join(' && ')`. Рядки не проходять `shellQuote`: це shell-текст користувача, як `config.args`
  у `buildFallbackCommand()`. `&&` реалізує рішення "зупинка на першій помилці".
- `tabName = entry.name` виставляється так само, як для інших Terminal-викликів. `runExecutionPlan()`
  сам відкриває іменовану MCP-сесію.
- Для такого виклику `commandSource = 'custom'`. `guessedCommands()` його не враховує, бо вгадування
  тут немає.
- `needsTerminalCommands()` рахує лише записи з `config`. План лише з власних команд не викликає
  `readIdeaRunConfigs`.
- Порти інспектора власним записам не призначаються (`mode` не `debug`).

## 4. Прозорість

`src/cli.js`: перед запуском (не лише під `--dry-run`) для кожної власної команди друкується рядок
`  seed db: npm i && npm run seed` через `log.info`. Причина: `webstorm-commands.json` лежить у
`.idea/` і зазвичай комітиться. Клонований репозиторій із сирим shell-текстом виконав би його при
першому `wsc`. Користувач має бачити, що стартує. `--dry-run` додатково показує
`→ execute_terminal_command  npm i && npm run seed` (наявний `formatExecutionPlan`).

## 5. Шлях без IDE

`src/fallback/terminalFallback.js`:

- `resolvePlan()` бере власні записи з `presetEntries` без каталогу `.idea`.
- Помилка "WebStorm has saved no run configurations" виникає лише коли в плані є запис, якому
  каталог потрібен. Пресет лише з власних команд працює й без збережених run-конфігурацій.
  Перевірка переноситься після побудови плану.
- `buildTabs()` для власного запису використовує `commands.join(' && ')` як команду і `name` як заголовок.
  `entry.config` там не читається (зараз є приведення типу на рядку ~155).
- `terminal` там уже означає `run`: дебагу немає, тому нового кейсу немає.

## 6. Екран `--configure`

`src/ui/configureLogic.js`:

- `buildInitialSelection()` додає власні записи до `choices` у тому порядку, як вони стоять у пресеті:
  назва вигляду `⌘ seed db — npm i && npm run seed`, `value` — ім'я, `checked: true`. У `stale` вони не
  потрапляють, бо це не посилання на IDE (інакше з'явилося б хибне "no longer exists in the IDE").
- `pendingModeQuestions()` власних записів не стосується: mode для них відомий.
- `applyAnswersToPreset()` зберігає власні записи цілими (з `commands`), якщо вони лишилися відміченими,
  на тих самих позиціях. Нові власні записи додаються після IDE-записів у порядку введення.
- `diffPreset()` показує `+ seed db` і `- seed db` без змін.
- Нова чиста функція `validateCustomName(name, {taken, ideNames})` повертає повідомлення про помилку
  або `null`. Відхиляє порожню назву, дублікат у пресеті та збіг із назвою IDE-конфігурації.

`src/ui/configure.js`:

- Після чекбокса і питань про mode йде цикл: `confirm("Додати власну команду?")`, потім `input` назви,
  потім `input` команд по одній. Порожній рядок завершує список, але перша команда обов'язкова: без неї запис не створюється.
  Невалідна назва перепитується з поясненням.
- `Prompts` розширюється до `{checkbox, select, input, confirm}`. Тести підставляють fake.
- Помилка "the IDE reported no run configurations to choose from" більше не завершує екран. Якщо IDE
  не повернуло конфігурацій, чекбокс показує лише власні записи (або пропускається, коли їх немає), а
  цикл додавання доступний завжди.
- Ctrl-C у будь-якому промпті нового циклу — звичайне скасування (код 130, нічого не записано).

## 7. Обробка помилок

| Ситуація | Результат |
|---|---|
| `commands` не масив або порожній, елемент не рядок, є `\n` | `PresetConfigError` (exit 1), назва файлу й запис |
| Власна назва збігається з IDE-конфігурацією при `--configure` | перепитування |
| Команда в послідовності падає в межах таймауту | існуюче `launchFailureReason()` за `command_exit_code`; `started N of M`, exit 1 |
| Довга команда (сервер) | `timeoutMs` рахується як started, як для інших терміналів |
| Помилка відкриття іменованої сесії | наявний fallback на спільну сесію з попередженням |

## 9. Ручна перевірка після реалізації

1. `wsc -c`, додати `hello` з двох команд, відкрити `.idea/webstorm-commands.json`.
2. `wsc --dry-run` — команди в `→ execute_terminal_command`.
3. `wsc` у живому IDE — вкладка з назвою `hello` (це також закриває нез'ясоване з CLAUDE.md:
   чи вкладка лишається з назвою після `close()` сесії).
4. `wsc --fallback=terminal` — вкладка ОС-терміналу з тим самим заголовком.
5. Команда, що падає першою, — друга не виконується, вкладка відкрита.
